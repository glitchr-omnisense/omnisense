**`Base\` and `App\`.** `omnisense/omnibase` 7.x holds the core of omnibase
sites under one namespace, `Base\`: the entities, the repositories, the
paginator, the behaviour attributes, the contracts, the services, the
templates. An application overrides `Base\X` by writing `App\X`, the same
path. The bridges add their framework and storage classes under `Base\`
too, so a site or a bundle names only `Base\` and `App\`, whatever runs
it: `omnibridge/symfony` 3.x under Symfony, `omnibridge/laravel` 2.x under
Laravel.

**Two persistences, one set of repositories.** `Base\Repository\*` is
written once - the finder language, `findBy()`'s criteria, `count()`,
`updateBy()`, `deleteBy()` - and runs on either engine:

- `omnibridge/doctrine` maps the entities with Doctrine ORM;
- `omnibridge/eloquent` reads the same tables into the same plain PHP
  entities with Illuminate's database layer (a data mapper: lazy ghosts,
  an identity map, casts), with the same lifecycle events.

Neither declares a repository of its own; both read the schema that
`omnisense/omnibridge` 2.x describes.

**omnibridge/doctrine 4.0.** The `datetime`, `datetimetz` and
`utc_datetime` columns are read as `\DateTimeImmutable` in UTC (DBAL 4.6
deprecates the mutable type); any `\DateTimeInterface` is still written,
in UTC, and the object given is left as it is. The columns do not change.
The types belong to the connection's type provider, no longer to DBAL's
static registry. `omnibridge/eloquent` 2.1 reads the dates the same way,
and `omnisense/omnibase` 7.1 takes an immutable moment wherever it took a
`\DateTime`. The upgrade notes are in the bridge's changelog.

**The manuals.** This website now documents the current series: omnibase
7.x, omnibridge/doctrine 4.x, omnibridge/symfony 3.x, omnibridge/eloquent,
laravel and twig 2.x, omnisense/omnibridge 2.x, the `omnibase/*` bundles
2.x and omnibase/docs 3.x. The former series stay published, with a notice,
out of search engines' indexes.
